01

Handshape Detection

The only module trained with machine learning. HamNoSys handshape isn't one label — it's a small compositional tree, so the model predicts it node by node.

A — Basic Handshape
fist / flat / spread / pinch / curved
C — Thumb Configuration
D — Finger-Type (straight / bent / hooked)
E — Finger States (which finger is active)
X — Extra (tip / nail / pad contact)

prediction is progressive — node A fires first, then conditionally activates C → D → E → X, so only legal tree paths can ever be produced

A→C→D→E A→D→E A→C→D A→C A→D A→E (1..n)

Why hierarchical, not one flat classifier?

  • Smaller, easier-to-separate classes per node → less confusion between visually similar handshapes
  • Mirrors HamNoSys's own compositional structure
  • Conditional prediction path makes invalid combinations structurally impossible
  • Trained with XGBoost (primary + fallback) and Random Forest on 63 features (21 landmarks × x,y,z) per hand image
02

Orientation Detection

Pure geometry — the palm/finger direction is computed from a vector, then rounded to the nearest of 8 evenly-spaced compass directions.

vec(p) = L_middle_base − L_wrist   |   n̂ = (−p_y, p_x)   |   360° / 8 = 45° per direction
right · 0° up-right · 45° up · 90° up-left · 135° left · 180° down-left · 225° down · 270° down-right · 315°

Why 45° wedges? 360° split evenly across 8 directions is the only partition where no direction gets a bigger slice — each spans ±22.5° around its canonical angle (boundaries ≈ 22°, 67°, 112°, 157°...).

The amber arrow marks one worked example: a computed palm-axis angle that lands inside the up-right wedge.

View selection (which reference frame): wrist above eye-level → bird view; wrist right of right shoulder → right view; otherwise → signer view.

3.3–3.4 — Finger & Hand Location

  • Active finger = largest extension from palm centroid, d_i = ‖ptip_i − ppalm‖
  • MediaPipe finger index ranges: thumb 1–4, index 5–8, middle 9–12, ring 13–16, pinky 17–20
  • Hand-in-frame zones use centroid C=(Cx,Cy) vs thirds: 0.33 / 0.66
  • Majority voting across frames smooths jitter (e.g. 3-to-1 vote → final label)

3.5 — Upper Body Location

  • d_norm = distance / (shoulder width, arm length, or torso height)
  • Shoulder: d_norm < 0.25 · Elbow: d_norm < 0.20 · Wrist: d_norm < 0.10
  • Torso: rel=(Cy−shoulder_y)/torso_height → chest <0.35, stomach 0.35–0.70, below ≥0.70

04

Movement Detection

Two layers: instantaneous frame-to-frame stats, then the shape of the whole path.

Movement-1 — direction / speed / repeat

Δp_t = p_{t+1} − p_t · ε = 0.02 dead-zone · v̄<0.01 slow, v̄>0.03 fast · reversals count repetition

Movement-2 — path shape / circularity

D = ‖p_N−p_1‖ (net) vs L = Σ‖p_{i+1}−p_i‖ (path length) → D≪L means circular/looped motion

turning angle θ_i = cos⁻¹( v_i·v_{i+1} / (‖v_i‖‖v_{i+1}‖) )  ·  rotation direction from dα/dt (clockwise if decreasing)

Validation & Avatar Verification

The project's only quantitative grading step, since no labeled test set exists for orientation/location/movement.

CSV Lexicon Validation

Every predicted combination is checked against a reference CSV of legal HamNoSys symbol strings + hex codes. Anything not on the list gets flagged and corrected — this is what makes "grammatically impossible" notation impossible to output.

Cosine Similarity

cos_sim(A,B) = (A·B) / (‖A‖‖B‖)

Compares the direction/pattern of the avatar's feature vector vs. the original — not raw magnitude, so mismatched avatar/human proportions don't distort the score. Worked example: 0.8812 similarity, RMSE/RMSD 0.2781.

PREP

Viva-Ready Q&A

The questions most likely to come up, answered short. (Full 12-question set is in the companion study guide.)

Why is handshape ML but orientation/location/movement geometry?
No public dataset links sign video to HamNoSys labels. A controlled image dataset was feasible for handshape; frame-by-frame video annotation for the other three wasn't. Geometry needs zero training data.
Why hierarchical handshape classification instead of one flat model?
Smaller, easier-to-separate classes per node reduce confusion between similar hand shapes, mirror HamNoSys's own compositional structure, and guarantee only structurally valid symbol paths are produced.
Why normalize coordinates everywhere?
So thresholds work regardless of camera distance, resolution, or the signer's body size — every distance is expressed as a fraction of a body reference (face height, shoulder width, torso height) instead of raw pixels.
Why cosine similarity for avatar verification?
It compares the direction/pattern of two feature vectors rather than raw magnitude, so it stays meaningful even though the avatar's proportions differ from the real hand's.
Difference between Movement-1 and Movement-2?
Movement-1 = instantaneous frame-to-frame stats (direction, speed, repetition, size). Movement-2 = the shape of the whole trajectory (curvature, circularity, rotation direction, oscillation) via displacement-vs-path-length and turning angles.
What's the ground truth, since no labeled HamNoSys dataset exists?
A self-built CSV mapping table linking gesture combinations to valid HamNoSys symbols + hex codes — used to train the handshape classifiers and as the legality check (lexicon) after prediction.
What are the honest limitations of this project?
Only handshape has a trained, dataset-backed model; the geometric thresholds elsewhere aren't validated against a large labeled test set. No aggregate accuracy numbers are reported for orientation/location/movement — evidence is qualitative plus one avatar similarity example. Continuous/connected signing is still an open problem, not fully solved here.
